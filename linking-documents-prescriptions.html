CASE STUDY

Linking Documents & Prescriptions

Lives inside OnePulse Connect's Global Inline Drawer, the panel that surfaces a patient's documents and prescriptions inline during dispensing. The drawer itself is background context here.

Linked Documents connects prescriptions and medications to the documents that support them, so staff can attach an incoming document to an existing patient record instead of restarting intake, and the system can resolve exactly which document prints when more than one could. I designed the interaction model and its guardrails.

ROLE: PRODUCT DESIGN (SOLO) TIMEFRAME: 2026 (IN PROGRESS AT DEPARTURE) STACK: FIGMA → CLAUDE CODE

01

Problem

Two separate views had no way to talk to each other. During OnePulse Connect's dispensing workflow, staff work across a documents tab (authorization letters, EOBs, signed prescriptions, consent forms tied to a patient) and a prescription tab (prescription info and the patient's medication list, different objects with different data behind them), both inside the Global Inline Drawer. Nothing connected the two.

BEFORE/AFTER, STATIC — DOCUMENT CARD & PRESCRIPTION/MEDICATION CARD, EACH WITH ITS "LINKED" SECTION REMOVED (BUILD FROM REAL CARD COMPONENTS)

The cost showed up as real, specific workflow problems. When a doctor sent an ERX for a patient already set up in workflow, staff had no way to attach it to the existing record, they had to restart intake from scratch. A single document, an authorization letter covering two dosage variants of the same drug, for example, sometimes needed to apply to more than one medication, and the system had no way to express that. We scoped the fix properly in a working session with the team on June 5, 2026.

02

Why This Matters

Jillian, who works documents from the patient profile rather than an active workflow, described hunting for an approval letter after a medication had already been dispensed, with no reliable way to find it by medication name. Staff were already renaming files "DO NOT USE" as a workaround, since there was no way to deactivate a document without deleting it.

There was also a sharper, safety-adjacent problem underneath. Once a document could be linked to multiple medications, "Print Prescription" needed to resolve to exactly one document, even with several Rx Prescription-type documents on file. Left ambiguous, the system either can't act or a staff member has to guess, in a clinical dispensing context. That's not something this tool could leave loose.

03

Component Documentation: Linked Documents

Checkboxes in a flat list were the first version, and they didn't work. There was no visible sign a document was tied to a medication, and real usability feedback confirmed it: the linking action wasn't explicit enough for people working under time pressure.

It had to work in both directions. From a prescription, a user opens Linked Documents and connects existing patient documents to it. From the documents side, uploading a new document lets a user tie it to one or more medications or prescriptions at upload time, in an optional Linked Medications & Prescriptions field. If nothing's selected, the document still uploads, it just lands on the patient's profile only.

HIGH PRIORITY, STATIC — UPLOAD FILE DIALOG, CROPPED TO THE LINKED MEDICATIONS & PRESCRIPTIONS FIELD + "OPTIONAL" HELPER TEXT

A two-zone layout fixed the visibility problem. The dialog splits into Linked to this Prescription (populated with whatever's already connected, or an explicit empty state) and All Documents (the full list, with a Link action per row). Clicking Link visibly moves a document from one zone into the other.

HIGH PRIORITY, CLIP — CLICK LINK ON A ROW IN ALL DOCUMENTS AND WATCH IT MOVE INTO LINKED TO THIS PRESCRIPTION, STARTING FROM THE EMPTY STATE. THE SINGLE MOST IMPORTANT VISUAL IN THE CASE STUDY

Built entirely from existing components, on purpose. Table Row, Button, and Alert all came from the system as-is, no new components shipped for this. Every flow like this is a chance to either extend the system's surface area or confirm what's already there is enough. Later, eRx records folded into the same model as their own document type, so a prescription received electronically and one that arrived as a fax could be linked, replaced, and referenced identically.

The system also needed a way to show a document was already linked elsewhere. A patient's file could easily hold a document, an authorization letter, for instance, that applied to more than one medication. What shipped is a muted "Also Atorvastatin 20 mg" line under the filename, visible only when that link exists.

MEDIUM PRIORITY, STATIC — STILL FRAME FROM THE TWO-ZONE CLIP ABOVE, ZOOMED ON THE "ALSO ATORVASTATIN 20 MG" LINE

That idea came straight out of the original working session. I proposed it live in that first meeting, and the team responded to it immediately. No existing design system pattern covered secondary metadata under a primary label that isn't a filename, so I flagged that gap rather than force an existing pattern to do something it wasn't built for.

04

Reasoning & Governance

The hardest problem in this feature was a guardrail: never let a prescription end up without a document backing it. Once "Print Prescription" depended on exactly one reference document, removing that document carelessly could leave a prescription with nothing behind it, a real risk in a system that dispenses medication. I designed the rule before it went through any formal review. Links stay freely editable before anything is saved, since nothing is committed yet. Once saved, the reference document can't be removed outright, a replacement has to be designated first. Linking a new Rx-type document while one is already the reference surfaces a "Linked Prescriptions Found" alert, asking whether to replace it, add the new one alongside it, or cancel, and replacing the reference always requires capturing a reason first: new Rx, updated Rx, a strength change.

HIGH PRIORITY, CLIP — LINKING A SECOND RX-TYPE DOCUMENT WHILE ONE IS ALREADY THE REFERENCE, SHOWING THE "LINKED PRESCRIPTIONS FOUND" ALERT APPEAR

When that logic went through review with Anardo (architecture) and Maribel (clinical), it held up without changes. Maribel's standard was direct: patient records are never deleted, and a prescription should never be left without a source document attached. The only legitimate reason to fully unlink is a patient-mismatch error, handled at the patient-record level, not in this dialog. Anardo confirmed the removal lock and the reason-capture requirement I'd already built matched that standard exactly. Neither Maribel nor Anardo asked for a single change.

MEDIUM PRIORITY, STATIC — SIMPLIFIED 4-5 STEP REDRAW OF THE REMOVAL GUARDRAIL (SAVE → LOCK → IS IT THE REFERENCE? → BLOCK OR REQUIRE REPLACEMENT), NOT THE DENSE FULL FLOWCHART

An AI assistant helped lay out candidate patterns for the reference-designation problem, weighed against what the design system already had. I chose a persistent row treatment and pushed it further: a left-stroke highlight, a "Reference Rx" tag, and a filled star that doubles as the toggle, kept always visible so it can't get missed in a fast-moving workflow.

MEDIUM PRIORITY, CLIP — CLICKING THE STAR TOGGLE ON A DIFFERENT DOCUMENT AND WATCHING THE LEFT-STROKE HIGHLIGHT AND "REFERENCE RX" TAG MOVE TO THAT ROW

"Associated Documents" and "+ Associate" tested as unclear with real users, so I proposed "Linked Documents" and "Link," which matched the two-zone interaction more directly. "Primary Rx" got the same scrutiny: flagged early as a placeholder since "primary" implied a ranking, when the real function was identifying which document prints. That eventually settled on "Reference Rx." And when my first version dimmed already-linked documents in the All Documents list, the team's simpler read, just remove the row once it's linked, was the right call, so I changed it.

05

The Design-to-Code Bridge

I built and iterated this as a working HTML/CSS/JS prototype, directed through Claude Code rather than hand-coded. I wrote the specs, reviewed every change against the design, and made the calls on naming, edge cases, and terminology. Claude Code wrote the markup and script changes to match.

Every prompt stayed scoped on purpose. Each one named exactly what should change, down to specific class names and IDs, and closed with an explicit instruction not to touch anything else, a guardrail against an AI-assisted change quietly drifting outside its scope, and a change log where every prompt maps to one reviewable diff. The Associated-to-Linked rename is the clearest example: it touched visible labels, CSS classes, JS function names, and data properties, and required spelling out exactly which needed to change and which structural IDs had to stay put.
