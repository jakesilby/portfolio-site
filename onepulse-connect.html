OnePulse Connect Design System

01

The Problem

No shared source of truth existed. OnePulse Connect had a component library when I joined, spread across different Figma files with no consistent naming and no shared token source. There was no single place designers or engineers could go to see how a chip, a card, or a table was supposed to look or behave.

I set out to fix that at the source: a token and component system other designers could work from directly in Figma, with clear rules for states, variants, and usage.

02

Why This Matters

Inconsistency here is a safety risk. The screens carry prescriber NPIs, drug NDCs, claim statuses, copay amounts, prior authorization steps. Without a shared library, the same status can look different depending on which screen a pharmacist or technician is looking at. Misreading a status on a controlled substance order risks the wrong drug reaching the wrong patient.

The platform runs at real scale. OnePulse Connect serves more than 2,000 provider locations across 29 states, managing nearly $1 billion in drug and supplies inventory.

A shared system was the only way to close that gap for good. Ad hoc fixes on individual screens would have left the same risk sitting everywhere else.

03

Token Architecture

No tokens existed at the start. Every screen hardcoded its own colors, spacing, and typography, decided fresh each time. I built a three-layer system as the foundation everything else sits on: primitives (raw values, no meaning attached), semantic aliases (primitives assigned a role, so "pulse-teal-500" becomes "primary"), and mapped tokens (aliases resolved into the specific tokens components actually consume, like bg-fill-default or fg-fill).

Components only ever reference the mapped layer, never a raw value. Change a primitive or alias and everything downstream updates without touching a single component file. It also became an enforceable rule for Claude Code: never hardcode hex values, always pull from tokens.css.

The result: 671 lines of fully resolved tokens.css, documented section by section: primitives, aliases, applied tokens by accent, action, component, text, surface, then typography, spacing, radius, border width, elevation.

04

Component Documentation

I fully documented 25 atoms and 16 patterns. The 3 global components exist in the coded library as well, but not to the same level of completion. Inline Drawer is the clearest gap: it didn't make it fully into code (more on that below).

Tab Group is the clearest example of a component built to solve a real problem. In Orders, a single drug can have multiple NDCs that regulatory and administrative rules require to stay together, never split across separate tabs the way different drugs are. I built Tab Group to keep those NDCs grouped under one drug, a gap caught during design before it ever shipped as a problem.

That documentation lives at the component level in Figma, alongside the token file. Every component includes its purpose, when to use it and when not to, an explanation of each property, layout behavior, common usage patterns, dos and don'ts, and accessibility considerations. Other designers used the system without me in the room because the documentation covered purpose, states, and usage directly, and the code translation worked from it later.

The same instinct shaped Data Table, the system's most consequential component. OnePulse Connect's core workflows (orders, claims, dispensing, inventory) all live in dense tables. I built two table types, Single Row and Tree Row, designed around AG Grid's capabilities from the start, since that's the framework engineering builds with.

The real work was in the rules underneath the visual layer: 15 grid cell content types (checkbox, chip, numeric, avatar & name, link, button group, and more), so any column is typed correctly instead of every table inventing its own formatting. Disabled rows cascade: every child component (links, chips, checkboxes, buttons) inherits the disabled state, so a disabled row can't leave a clickable action behind by accident. Tree rows go one level deep, and pagination treats a parent-plus-children group as a single unit that never splits across pages. I built custom checkbox/radio styling off native input state, keeping focus and keyboard behavior intact.

I flagged every gap explicitly. I mark a token assignment [NEEDS VERIFICATION] when it can't be verified against Figma dev mode, done over a hundred times across the docs.

05

Adoption in Production

By the end, all three designers on the team, myself included, built from this system in Figma as their default. New flows, one-off screens, static files: all of it came from the same shared components and tokens, not recreated individually each time.

The coded library showed a different pattern this early. Adoption of the coded component library for rapid prototyping was just beginning as I wrote this case study: real, but nowhere near the norm the Figma system had become.

The clearest proof of the system's value came from auditing it against what had already shipped.

06

Reasoning & Governance

The clearest example of this system's reasoning came from an investigation. Auditing the production codebase, I found three different reds in three different places (the token file, the component library, a hardcoded value in a live button), and none of them agreed.

I traced it to source instead of guessing. The component library's red matched Figma directly; the token file's value had no clear origin anywhere else. That ruled out treating the token file as correct by default. Confirmed against Figma, corrected the token file at the source.

The fix surfaced something bigger: the app wasn't consistently reading from the token system at all. Part of the codebase referenced raw primitives directly instead of the semantic layer meant to sit between design intent and implementation. I corrected that too, wiring the reference back to the proper layer so future token changes reach the app automatically. The fix went through review and shipped to production.

That same instinct, trace it, don't guess, shows up in smaller standing rules too:

  • “(Required)” instead of an asterisk on required fields, since a word doesn't depend on the reader already knowing a convention.
  • Disabled buttons use a distinct token set built specifically for the disabled state. Getting this wrong in a clinical tool means a disabled action can read as available.

07

The Design-to-Code Bridge

This part of the project served two purposes. Claude Code translated the Figma system into working code, but not blindly. There were moments it pulled from older, outdated token values instead of the current source of truth in tokens.css. I checked its output against tokens.css directly rather than assume it was current, and corrected the references when they didn't match. The same instinct that caught three conflicting reds in production applied here too: trace it, don't guess. I also meant it to be useful on its own: a coded component library designers and PMs could pull from directly for fast, consistent prototyping instead of redrawing screens by hand each time.

This same discipline extended to AI-generated copy: I triage it the same way. I flag and log a genuine gap. I remove anything that looks plausible but isn't grounded in the design system.

I finished Figma first; the code translation reached most of the way there.

The gap this closes: designers had a polished Figma library, but every prototype meant redrawing screens by hand, and every engineering handoff meant re-translating specs into code. I used Claude Code to bring the system into CSS/HTML directly: working components designers could pull for prototyping, and a faithful reference for an eventual React/Storybook conversion.

Most of the system made it into code: 25 atoms and 16 patterns exist as real, working HTML/CSS pages with their own documentation, in a structured repo with a live browsable site. All 3 globals have a presence in that same repo, but Inline Drawer is the clearest gap, more time-intensive to translate than scoped for; I've only partially built it.

I logged every gap explicitly. Missing shadow tokens, expiring asset URLs, undocumented layout details: each one recorded with the decision made to fill it, dozens of entries deep on components like Data Table alone.

React and Storybook never happened. I meant that to be the next step, building on a largely-complete vanilla library.

08

What's Next

Two kinds of remaining work. Scoped and known: finish the remaining global components (including Inline Drawer), close out flagged NEEDS VERIFICATION and gap-log items. Bigger step: convert the vanilla library into React and get it into Storybook, so engineering has the same source of truth designers already have in Figma.

I don't have the resources to finish Inline Drawer for this case study. Its cost outgrew its scope partway through, and I chose to stop rather than force it.

This project left me with a working, base-level understanding of design systems and what it takes to translate one into code. It also pushed me toward wanting to go deeper into front-end and design engineering next. Closing the Storybook and React gap this case study left open is high on that list.
